# Shared Qdrant Proxy

## Status

Implemented (MVP) in `hybridInference`.

This document describes the current implementation that powers shared codebase indexing
for Roo Code and Kilo Code.

## Problem and Goal

Roo/Kilo codebase indexing needs both:

- an embedding endpoint (`/v1/embeddings`)
- a vector database endpoint (Qdrant-compatible API)

Without a shared service, every user must run local Qdrant. The goal is to expose a
managed Qdrant endpoint through the API gateway so users only configure URLs and API keys.

## Architecture

```text
Roo/Kilo Plugin
  ├─ Embeddings  -> https://freeinference.org/v1/embeddings
  └─ Vector Ops  -> https://freeinference.org/v1/qdrant/...
                      |
                      v
                FastAPI Qdrant Proxy
                      |
                      v
                 Internal Qdrant
```

If Cloudflare is enabled, traffic still reaches Nginx at origin before FastAPI. Request-size
limits at Nginx can block indexing requests before they reach the proxy.

## Code Map

- `serving/config/settings.py`
  - `qdrant_base_url` (default: `http://localhost:6333`)
  - `qdrant_api_key` (default: empty)
- `serving/http.py`
  - `AsyncHTTPClient.request(...)` for raw method/body forwarding
- `serving/servers/routers/qdrant_proxy.py`
  - shared Qdrant reverse proxy router
- `serving/servers/app.py`
  - router registration

## Public API Surface

The proxy route is:

- `/v1/qdrant/{path:path}`

Supported methods on the proxy route:

- `GET`, `POST`, `PUT`, `PATCH`, `DELETE`

Allowed path patterns (anything else returns `403`):

- `GET /v1/qdrant/`
- `/v1/qdrant/collections`
- `/v1/qdrant/collections/{collection}`
- `/v1/qdrant/collections/{collection}/points`
- `/v1/qdrant/collections/{collection}/points/search`
- `/v1/qdrant/collections/{collection}/points/scroll`
- `/v1/qdrant/collections/{collection}/points/recommend`
- `/v1/qdrant/collections/{collection}/points/delete`
- `/v1/qdrant/collections/{collection}/points/count`
- `/v1/qdrant/collections/{collection}/points/payload`
- `/v1/qdrant/collections/{collection}/index`

## Authentication and Security

### Client authentication

The proxy always requires authenticated users.

Even if global `USER_AUTH_ENABLED=0`, anonymous requests to `/v1/qdrant/*` are rejected
with `401`.

Accepted client auth headers:

- `Authorization: Bearer <FREE_INFERENCE_API_KEY>`
- `X-API-Key: <FREE_INFERENCE_API_KEY>`
- `api-key: <FREE_INFERENCE_API_KEY>`

If only `api-key` is provided, the proxy maps it to a Bearer token check internally.

### Upstream Qdrant authentication

The proxy injects internal Qdrant credentials using server config:

- `QDRANT_API_KEY` -> forwarded as `api-key` to upstream Qdrant

Clients never need to know the internal Qdrant API key.

## Tenant Isolation Model

Collection names are scoped per user:

- External collection name: `workspace-index`
- Internal collection name: `fi_{sha256(user_id)[:12]}_workspace-index`

Isolation behavior:

- Requests targeting `/collections/{name}` are rewritten to scoped names.
- `GET /collections` is filtered to only current user's scoped collections and names are
  de-scoped in the response.
- `GET /collections/{name}` response de-scopes `result.name`.

This prevents cross-user collection discovery through list APIs.

## Error Semantics

- `401`: missing/invalid Free Inference API key
- `403`: endpoint outside allowlist
- `502`: proxy cannot reach upstream Qdrant (`aiohttp.ClientError`)
- `413`: usually generated by Nginx before FastAPI when request body exceeds Nginx limit

## Deployment Requirements

Set environment variables for the API server:

```bash
QDRANT_BASE_URL=http://127.0.0.1:6333
QDRANT_API_KEY=<internal-qdrant-api-key>
```

If `QDRANT_API_KEY` is empty, proxy requests are still forwarded, but upstream Qdrant may
reject them when auth is enabled.

## Nginx Configuration for Large Upserts

Codebase indexing may send large `/points` upsert payloads. Nginx default
`client_max_body_size` is often `1m`, which can cause `413 Request Entity Too Large`.

The checked-in config (`infrastructure/nginx/freeinference.conf`) sets `client_max_body_size 50m`
on the `/v1/` location block, which covers all API traffic including Qdrant upserts:

```nginx
location ^~ /v1/ {
    client_max_body_size 50m;
    proxy_pass http://freeinference_api;
    ...
}
```

Then validate and reload:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## Verification Checklist

1. Authenticated collections call returns success:

```bash
curl -sS https://freeinference.org/v1/qdrant/collections \
  -H "Authorization: Bearer <FREE_INFERENCE_API_KEY>"
```

2. Unauthenticated request is rejected:

```bash
curl -i https://freeinference.org/v1/qdrant/collections
```

3. Endpoint allowlist is enforced:

```bash
curl -i https://freeinference.org/v1/qdrant/snapshots \
  -H "Authorization: Bearer <FREE_INFERENCE_API_KEY>"
```

4. Roo/Kilo indexing succeeds with:

- Qdrant URL: `https://freeinference.org/v1/qdrant`
- Embedder provider: `OpenAI Compatible`
- Embedder base URL: `https://freeinference.org/v1`

## Debugging Playbook

1. Check API response code first (`401/403/413/502`).
2. If `413`, inspect Nginx logs:

```bash
sudo tail -f /var/log/nginx/freeinference.error.log
```

Look for `client intended to send too large body`.

3. If `502`, verify Qdrant health from API host:

```bash
curl -sS http://127.0.0.1:6333/collections \
  -H "api-key: <internal-qdrant-api-key>"
```

4. Check backend logs:

```bash
journalctl -u hybrid_inference.service -f
```

## Current Limitations

- This is not a full passthrough of every Qdrant admin endpoint.
- No vector-usage quota enforcement yet.
- No dedicated vector operation audit table yet.

These are intentional MVP tradeoffs to keep the shared service safe and stable.
